Two machines, one job

The parts a regex can do exactly stay in code, where they're fast and provable. The part a regex can't express goes to the model.

code · exact

A lenient tokenizer, run locally, before anything hits the model.

  • countevery tag, element type, self-closer, exact
  • depthmax nesting, no estimates
  • balancewhich tags never close, listed by name

model · judgment

One forward pass, typed answers, calibrated probabilities.

  • matchdoes the document match your plain-language pattern
  • well_formedstructural verdict with confidence
  • anythingpatterns you can name, not just patterns you can compile

What it won't do

The model's own documentation lists its limits. We design around them instead of pretending.

It doesn't count reliably

Counts are computed in code and shown in the deterministic panel. Ask the model "how many" and it guesses; that's on us to not do.

It doesn't extract spans

No text generation, so no "give me the exact substring". It judges; it doesn't quote. Use a parser for the quote.

Huge states cost accuracy

Context rot is real, so input is capped at 60k characters. That's plenty of real-world pages and stays inside the state budget.

It reads literally

The pattern you type is the pattern it judges, at face value. Write it the way you'd explain it to a careful intern.
